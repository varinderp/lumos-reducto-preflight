# Lumos

Lumos estimates the cost of a Reducto document pipeline before the paid job
starts. It is split into two pieces:

[Live demo](https://lumos-reducto-preflight.varinder.chatgpt.site/)

1. A browser simulator for documents, pipeline settings, and budget policy.
2. `POST /api/estimate`, which runs the same pricing engine inside an app's
   upload flow.

The simulator is organized as **1. Documents**, **2. Pipeline configuration**,
**3. Policy**, and **4. Estimate**. It starts without an applied pipeline:
uploading documents records their local metadata, but Lumos waits for a
configuration created with **Set up manually** or **Import from Reducto** before
calculating an estimate. The visual builder uses five endpoint tabs in this
order: Parse (standalone), Classify, Extract, Split, and Edit. Standard Extract
is selected as an inactive example until **Apply configuration** is selected.

Each endpoint pane contains its cost-relevant settings and a separate
**Additional inputs** area for estimator-only values. The builder generates the
strict Lumos profile internally, so simulator users never need to write
object-or-null pipeline JSON themselves. The active pane scrolls within its
fixed-height window, then passes continued wheel or touch scrolling to the page
at either boundary. The tabs and **Apply configuration** action stay visible.

**3. Policy** contains the **Maximum cost, USD** budget input and the **Default
rate card** link. The link opens every unit price used by the calculator.
Applied edits change simulator estimates for the current browser session only.
They are never added to API requests; the API, generated preview, and public
request schema remain unchanged and continue to use Lumos's built-in public
rates.

The page also contains an optional paid verification form. That path uploads
real files to Reducto, runs a deployed pipeline, and returns Reducto's usage
fields without returning or storing extracted document contents. It accepts a
Reducto API key and pipeline ID at runtime, forwards them only for that request,
and does not persist them. Running verification may incur Reducto charges.

## Run locally

Node.js `>=22.13.0` is required.

```bash
nvm use
npm ci
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). No environment variables
or Reducto credentials are required for the simulator or estimate API. Run the
complete validation suite with `npm test` and lint with `npm run lint`.

## Deploying a fork

The checked-in `.openai/hosting.json` uses a placeholder project ID. Replace it
with your own Sites project ID before deploying a fork; it is not needed for
local development. Protect public deployments with authentication and rate
limiting, especially the paid `/api/reducto` verification route.

## Estimate API

```http
POST /api/estimate
Content-Type: application/json
```

The request sends document metadata, the Lumos profile generated by the
simulator, and an optional budget. Lumos receives metadata only; it never
receives the document files or their contents.

| Field | Required | Description |
| --- | --- | --- |
| `documents` | Yes | An array of metadata rows. Each item contains the original filename in `name` and its page count in `pages`; do not send file contents. |
| `pipeline` | Yes | The Lumos profile generated after the simulator applies a configuration, whether it was set up manually or imported from Reducto. Store this profile in the application. |
| `policy.max_total_usd` | No | The maximum acceptable job cost in USD. It defaults to `10` when omitted. |

**Copy Lumos profile** is available beneath the simulator's configuration inputs
only for a clean applied configuration. Whether the configuration was created
manually or imported from Reducto, Lumos first converts it into the same
generated Lumos profile. The copy action includes only that generated profile,
not documents, policy, custom rates, or preserved Reducto JSON. The application
owns storage; Lumos does not host profiles or issue profile IDs.

A server can load that stored profile and add the upload metadata and policy:

```js
const pipeline = await loadLumosProfileFromServerStorage();

const response = await fetch("https://your-lumos-site/api/estimate", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    documents: uploadedDocuments.map(({ name, pages }) => ({ name, pages })),
    pipeline,
    policy: { max_total_usd: 10 },
  }),
});
```

```json
{
  "documents": [
    {
      "name": "contract.pdf",
      "pages": 18
    }
  ],
  "pipeline": {
    "parse": null,
    "classify": {
      "page_range": { "start": 1, "end": 5 }
    },
    "extract": {
      "settings": { "deep_extract": false, "optimize_for_latency": false, "include_images": false }
    },
    "split": null,
    "edit": null,
    "lumos_assumptions": {
      "conditional_extract_routing": false,
      "estimated_extract_fields_per_page": 24
    }
  },
  "policy": { "max_total_usd": 10 }
}
```

The response contains `low_usd`, `likely_usd`, `high_usd`, priced Parse,
Classify, Extract, and Split page counts, `estimate_complete`, any
`unpriced_cost_factors`, and an `allow`/`review`/`deny` decision. Parsing is
already included in the displayed Extract and Split prices.

Production integrations should call Lumos from an authenticated server rather
than treating a browser request as a trusted budget control.

After a simulator configuration is applied, the API section exposes a collapsed
**View this simulator's API request and response** disclosure containing the
**Request preview** and **Response preview**. It has no second profile-copy
action.

This interface cleanup does not change the public API contract, estimator,
pricing behavior, policy decisions, importer, or unsupported-spreadsheet
boundary.

The profile is a Lumos input, not a Reducto request body. Documented Reducto
settings retain their API names, while uncertainty and derived values are kept
inside `lumos_assumptions`. The API rejects unknown request, document, and
pricing-profile fields, so a typo or unsupported operation cannot silently
produce a lower estimate; use **Import from Reducto** in the simulator to
translate supported Reducto JSON configurations.

API callers may optionally send `documents[].assumed_extract_route` when their
own application already knows that a document will use Standard or Deep
Extract. Omitting it leaves conditional routing unknown and produces the
corresponding range. The browser simulator does not supply this API-only
override; it derives its document labels from the applied pipeline and models a
conditional Extract configuration as unknown before routing.

## Import from Reducto

The simulator can build the Lumos cost profile from the JSON configuration shown
inside each operation in a Reducto pipeline. Paste one or more operation
configurations as adjacent JSON objects, or paste an array of configuration
objects. If a pipeline contains Parse and Extract, paste both configurations so
Lumos can account for their combined settings.

Applying an import replaces the complete Lumos pipeline profile. It never merges
with the previously applied profile, so an omitted operation cannot remain
enabled accidentally. Document rows, edited page counts, and the budget stay
unchanged. Both **Set up manually** and **Import from Reducto**
use the same **Apply configuration** action.

The manual builder has one tab for each supported endpoint, ordered Parse
(standalone), Classify, Extract, Split, and Edit. Every tab shows whether the
endpoint is on or off, and its active pane contains only that endpoint's
cost-relevant settings. Estimator-owned values appear under **Additional
inputs**. Document totals sit above the internally scrolling builder; continued
scrolling at the pane's top or bottom moves the page. The endpoint tabs and
**Apply configuration** remain visible. The tab order is for navigation and
does not define Reducto execution order.

The visual builder treats **Parse (standalone)** as a separately priced job, so
its switch is mutually exclusive with Extract and Split. Classify and Edit may
still be combined with it because they add separate charges. Extract and Split
already include parsing in their rates. This constraint belongs only to the
simulator builder: the public API continues to accept its existing bundled
Parse profile shape for compatibility.

The builder creates cost-focused Reducto configuration fragments, not a complete
deployable Reducto pipeline. Full schemas, formatting, retrieval, split
descriptions, and other accepted cost-neutral authorship come from imports. An
import keeps a safe per-endpoint copy of that accepted JSON for review while
mapping the cost fields into the Lumos profile. After an import is applied,
**Review setup** opens the builder with those mapped settings; accepted neutral
fields remain preserved rather than being discarded.

Lumos infers Parse, Extract, Split, Classify, and Edit from documented,
operation-specific configuration keys. Important Reducto field paths include:

- Parse `enhance.agentic` and `settings.page_range` configure agentic scopes and
  page selection;
- standalone Parse `queue_priority: "batch"` models Reducto's Batch Parse
  execution choice;
- `settings.deep_extract: true` selects Deep Extract;
- `settings.optimize_for_latency: true` applies Reducto's documented 2× Extract
  cost;
- `settings.include_images: true` preserves the setting and requires review for
  its unquantified cost increase;
- `instructions.schema` supplies a conservative static Extract field count when
  its shape is bounded;
- Classify `page_range` controls priced context pages;
- the current Deep Split setting is `settings.deep_split`, with page selection
  under `parsing.settings.page_range`; and
- Studio JSON with top-level `deep_split` and `split_options` is accepted as a
  compatibility shape and normalized to the current Lumos profile.

Inputs that Reducto cannot supply before processing stay visibly separate under
**Additional inputs**. These include the expected Complex Parse share, expected
chart counts, conditional Standard/Deep Extract routing and its likely Deep
share, expected Extract fields per page, and known fully prefilled Edit pages.
They remain serialized under `lumos_assumptions` and are estimator inputs, not
fields to copy into a Reducto pipeline.

Paste a Parse configuration alongside Extract or Split so Lumos can recognize
that parsing is bundled into the downstream operation. Imported bundled Parse
settings remain accepted and preserved, but the review builder represents them
as included downstream rather than turning on **Parse (standalone)**. Lumos does
not add a separate Parse line or separately priced Parse range because the
current Extract and Split rates include parsing. Extract and Split keep
independent page ranges. When the builder reviews an older bundled profile whose
only range is on Parse, it transfers that range to any downstream operation that
lacks its own range so reapplying remains cost-equivalent. A standalone Parse
configuration is priced from the Standard and Complex page rates, with any
agentic multiplier and batch-queue discount read from the profile.

Edit is always a separate additive line item. Its built-in public rates are $60
per 1,000 pages and $15 per 1,000 known fully prefilled pages; an applied custom
simulator rate card may replace those values for the current browser session
only.

Standalone Parse returns low, likely, and high values because the Standard and
Complex page mix is known only after processing. The likely value uses the
visible `likely_complex_parse_share` assumption and defaults to 50%. When
Advanced Chart Agent is enabled, a developer may provide likely and maximum
detected-chart counts. Without those counts, Lumos still returns the known page
estimate, marks it incomplete, and identifies the excluded chart charge.
Because queue priority is an execution-time choice rather than a Studio operation
configuration, add `queue_priority: "auto"` or `"batch"` to the standalone Parse
section of the Lumos profile when needed.

Split page selection is stored at Reducto's documented
`split.parsing.settings.page_range` path. Extract keeps its own normalized
page-range field. The visual builder labels these independently so a developer
can see exactly how many pages each downstream endpoint will price.

Agentic work, figure summarization, complexity, and Advanced Chart Agent do not
create a separate Parse line when parsing is bundled into Extract or Split.

Page selections are 1-indexed, inclusive, deduplicated, and capped at each
document's page count. When a bounded schema is present, Lumos counts its static
leaf fields. Arrays, missing schemas, and ambiguous schema shapes add
`extract.field_density` as an unpriced factor and force review because the final
field density can cross Reducto's surcharge threshold.

The importer parses JSON only in browser memory. It does not execute the pasted
content, send it to Reducto, or persist it. Malformed JSON, conflicting
operation configurations, and ambiguous cost-relevant values fail closed: no
estimate is produced and the applied profile stays unchanged.

Any `spreadsheet` configuration group is informational because Reducto Studio
may include it for ordinary documents. It does not prove that the input is a
spreadsheet, even when settings inside that group are enabled. Only an
uploaded spreadsheet filename or document metadata identifying spreadsheet
input enters the unsupported state, because a page-priced estimate would be
invalid.

## Boundaries

- The simulator keeps selected files only in browser memory.
- Simulator rate edits stay in page state, apply only after **Apply rates**, and
  return to the built-in public values when the session is cleared or refreshed.
- The rate-card editor changes ten unit prices only. Agentic Parse and latency
  priority remain fixed at 2x, and Batch Parse remains a fixed 20% discount.
- Simulator rate edits do not alter `POST /api/estimate` or its public
  `rate_card` response identifier.
- PDF page counting is best-effort and editable.
- The simulator does not estimate until a valid pipeline profile is applied.
  Editing or invalidating that profile pauses the estimate, and clearing the
  session returns the simulator to its initial unconfigured state.
- Document processing labels are derived from the applied pipeline. The
  simulator does not ask users to choose a per-document Extract route.
- Classify PDF ranges are 1-indexed and inclusive. For non-PDF documents,
  Reducto ignores `page_range`, so Lumos uses the default first-five-page context.
- List pricing is based on Reducto's published rates effective September 1,
  2026. Contract rates can differ.
- Spreadsheet requests are rejected instead of being guessed from page counts;
  they require billable cell counts and the customer's own rate card.
- The JSON importer treats every `spreadsheet` configuration group as a
  nonblocking caution because operation config contains no input file metadata.
- An uploaded spreadsheet filename or spreadsheet document metadata blocks a
  page-priced estimate.
- Extract latency priority is calculated at 2x. Extract image context keeps the
  policy result at `review` until a numeric public or customer rate is available.
- Unbounded Extract field counts also keep the policy result at `review` until
  actual usage or a safe bound is available.
- A direct API Extract profile without `estimated_extract_fields_per_page` keeps
  its page estimate visible but incomplete; supply a safe whole-number bound to
  make the dense-field check complete.
- A known Extract profile at 100 fields per page is supported. Above 100, Lumos
  keeps the base estimate visible and marks the unpublished dense-field surcharge
  as incomplete.
- A range is expected when routing is conditional. Reducto's actual response is
  the reconciliation source after the job runs.
- Standalone Parse ranges use a visible Complex-page assumption. Conditional
  Extract ranges use the developer-supplied routing assumption. Neither path
  runs paid Reducto samples.
- `queue_priority: "batch"` applies the documented 20% discount only to
  standalone `/parse_async` work.
